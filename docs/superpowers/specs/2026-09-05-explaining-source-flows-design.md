# `explaining-source-flows` 技能设计

## 目标

创建一个独立技能，专门从当前仓库还原一条指定模块链路，并为开发者生成两份事实一致、阅读目的不同的文档：源码追踪版用于定位代码和逐步调试，技术讲解版用于快速建立可运行的心智模型。

该技能聚焦一条执行链，不替代 `tracing-source-modules` 的模块全景分析，也不默认生成独立的存储、异常、集成等专题文档。

## 技能身份与触发范围

- 技能名：`explaining-source-flows`
- 默认允许自动发现与调用。
- 适用于用户要求追踪、解释或讲清某个业务动作、接口、消息消费或后台任务的完整源码执行链。
- 当用户要的是模块级全景、数据流、存储、异常和集成关系的完整文档集时，应使用 `tracing-source-modules`。
- 当用户只问单个类、单个方法或局部代码含义，且无需跨组件追踪时，不应触发本技能。

## 输出结构

用户未指定位置时，输出到：

```text
docs/module-analysis/<module>/flow/
├── 01-source-trace.md
└── 02-developer-explanation.md
```

如果目标目录已有文件，只更新技能拥有的这两个文件，并保留其他内容。

## 源码追踪版

`01-source-trace.md` 面向需要查代码、下断点或核对行为的开发者。它应：

1. 从真实入口开始，追踪到当前源码可以证明的终点。
2. 先给出包含同步和异步边界的执行总图，再按实际执行顺序展开。
3. 每一步记录调用方与 `Class.method()`、输入来源、关键参数或对象、条件分支、核心操作、状态变化、返回值及下一调用方。
4. 对重要条件使用分支表或独立分支链，不能把互斥路径拼成一条虚假的主流程。
5. 明确事务范围、异常捕获或传播、远程调用、数据库操作、缓存操作及消息生产和消费边界。
6. 为重要事实提供仓库相对路径与方法或类型名，使读者能够直接定位源码。

其精度目标是：开发者可以根据文档设置断点，并按顺序观察链路运行。

## 技术讲解版

`02-developer-explanation.md` 面向第一次接触该模块、但具备开发背景的读者。它应：

1. 使用与源码追踪版相同的执行范围和事实基础。
2. 先解释模块入口、完成条件及其在系统中的作用，再沿执行顺序讲解。
3. 围绕“为什么有这一步、它接收什么、做了什么、交给谁、对系统有什么影响”组织内容。
4. 解释理解当前链路所必需的框架机制，例如参数绑定、过滤器、事务代理、ORM 持久化、Kafka 异步消费；不扩展成通用框架教程。
5. 主动指出开发者容易误判的语义，例如同步接口返回与异步最终完成不是同一时刻。
6. 保留关键类型、方法、字段、状态值和组件名，但省略不影响理解的局部实现噪声。
7. 通过源码链接连接到追踪版中的精确位置，避免复制大段细节。

其精度目标是：开发者读完可以用自己的话解释链路，并能判断下一步应去哪个组件或源码位置排查问题。

## 证据与追踪规则

- 结论必须来自当前仓库源码、配置、映射、DDL 或测试；不得用框架惯例代替证据。
- 同时搜索调用方和被调用方，并检查链路涉及的 DTO、实体、消息、枚举、配置与持久化映射。
- 对异步延续，必须找到真实的 Topic、队列、回调、调度器或持久化状态连接。
- 实体字段被修改不等于已经持久化；必须确认 `save`、mapper、SQL 或事务刷新行为。
- 声明了异常处理、幂等、回滚或重试不等于真实生效；必须确认调用路径和作用范围。
- 无法由源码确认的内容标为 `源码暂时无法确认`，业务上可能需要但未实现的保证不得写成现状。
- 技术讲解版可以解释源码事实的意义，但不能引入追踪版未证实的新事实。

## 一致性与验收

两份文档完成后应交叉检查：

- 入口、终点、主路径和所有重要分支一致。
- 类型、字段、状态值、存储名称、消息名称及同步/异步边界一致。
- 技术讲解版中的每项运行时事实都能在源码追踪版或其引用源码中找到依据。
- 所有源码链接有效，关键调用没有只列名称而不解释输入和输出。
- 执行总图能够独立回答：谁发起、输入是什么、经过哪些关键步骤、状态如何改变、何时返回、谁继续处理。
- 源码追踪版足以支持逐步调试；技术讲解版足以支持开发者复述和故障定位。

## 技能资源

技能保持自包含，只创建 `SKILL.md` 与 `agents/openai.yaml`。当前流程不需要确定性脚本、模板资产或大型参考文件；双文档规范直接写入 `SKILL.md`，避免加载与任务无关的资源。

## 验证策略

1. 使用技能初始化器创建规范目录和 UI 元数据。
2. 使用技能校验器检查名称、YAML frontmatter 和未完成占位符。
3. 以当前仓库“文件上传链路”为现实场景，静态检查技能能否引导出双版本文档、保留异步边界并区分两份文档职责。
4. 检查描述只表达触发条件，不把工作流塞进描述而导致模型跳过正文。
5. 检查技能与 `tracing-source-modules` 的边界明确，不发生输出职责重叠。
